## MVP 建议

**推荐的首期闭环：**本人在中台正在本机运行时，启动一个本地网页即可看到当前任务、进展和需要处理的事项，并能按规则翻历史、打开一轮时间线；首期验证“无需逐个执行 CLI，也能弄清任务状态”的价值。

| 范围 | 需求引用与能力 | 保留／推迟的理由 | 去向 |
|---|---|---|---|
| 首期包含 | 方案“本地启动与访问、总览、轮次状态表达” | 去掉后无法形成可打开、可理解的实时任务看板 | M1 |
| 首期包含 | 方案“自动与手动刷新、刷新失败与迟到响应、只读与内容安全” | 自动进展更新及本地密钥、只读边界是核心链路的必要完整性，不能留到上线前补 | M1，M3 做真实环境复核 |
| 首期包含 | 方案“历史筛选与分页、单轮详情” | 只有当前状态无法回答“之前发生了什么、为什么失败”，核心价值不完整 | M2 |
| 首期包含 | 方案“中台兼容”及浏览器人工验收 | 必须证明实际中台与真实浏览器可用，不能只靠代理和纯函数测试 | M3 |
| 首期推迟 | 回答、结案、停止、规则控制 | 用户已明确选择只读，现有 CLI 和飞书仍可处理 | 后续增量，未排期 |
| 首期推迟 | 按 `rule + lane` 聚合、待复查视图、SSE | 用户已选择按规则和轮次及轮询；这些需要新增中台字段和投影 | 后续增量，未排期 |
| 首期推迟 | 远程访问、桌面应用、开机自启动 | 本地手动打开已能验证核心价值 | 后续增量，未排期 |

- 成功判据：在临时真实中台与本地浏览器中，用户可看到总览、筛选规则、翻历史、打开详情，并观察到中台停止时的错误与恢复后的更新；对应方案验收矩阵全部 L0–L1 行及“浏览器总览、筛选、详情与恢复”L4 行。
- 价值反馈：工程验收后由本人进行一次真实任务试用，收集“能否快速找到需要处理的任务、状态文案是否容易理解、历史详情是否足以定位问题”的反馈；未取得前不宣称 MVP 价值已验证。
- 主要风险与前置验证：无阻塞技术假设，方案已明确不需要预研。新仓库远端尚未确定，只影响最终 MR，不影响本地实现和验收。
- 取舍与待决定事项：MVP 范围沿用已定版方案，无范围待决项；远端仓库在最终 MR 前确定。
