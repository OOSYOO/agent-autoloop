## MVP 建议

**首期闭环沿用已确认方案：**本人被列为 Reviewer，或在飞书收到明确审查委托后，自动审查当前 MR，并依照现有 publication 策略发布或等待本人确认；CI 在整个过程中不阻塞。只完成扫描放行不能交付这个价值，因为执行和发布仍可能被拦截。

- 成功判据：方案“验收矩阵与交付检查”全部六行在 L0/L1 隔离环境通过，证明两入口、报告、评论及本人确认接续不受 CI 影响，旧配置与历史记录兼容，原有授权边界有效。
- 价值反馈：工程交付后，目标环境升级和试用由本人安排。观察真实请求是否仍出现 CI 阻塞、两入口是否重复审查、评论是否按预期发布。尚无真实环境证据，不能用测试通过或 PR 就绪代替已上线可用。
- 主要风险：当前分支混有其他任务改动，且飞书入口尚未提交；实施前需核对 PR 的累计差异及依赖归属，不能把其他任务的整批差异纳入本次提交。旧 policyHash 和带 ci 的历史覆盖记录是主要兼容风险，按方案既定矩阵回归，不改写历史数据。
- 前置验证：技术方案已定稿，无阻塞预研要求；无需联网读取真实 MR 或发送真实消息来启动实现。
- 取舍：本次需求已构成最小完整闭环，全部进入一个里程碑，不拆出“只放行扫描”的半成品阶段；无新的产品范围待决项。

1. 核对当前差异归属和飞书入口依赖，记录 deliver 起始版本与测试基线。若原有依赖未进入远端提交，收尾时明确列出，不静默提交他人任务。

5. 运行 `npm run test:quick`、`npm run typecheck`、`npm run format:check`，执行独立审查并修复问题。若实际修改超出方案判断的范围，按 AGENTS.md 与 `scripts/ci-scope.sh` 扩展检查，不为过测改掉保留边界的断言。
6. 精确提交本任务，更新交付证据与本计划，再对整个本次范围完成累计差异审查、PR 和最终 CI；保留其他任务未提交文件并说明归属。
